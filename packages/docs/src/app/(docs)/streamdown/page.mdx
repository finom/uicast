# Streamdown plugin

`@uicast/streamdown` puts generated UI inside a Markdown chat reply. With the
raw-JSONL setup from [Streaming](/react/streaming), the model's entire output
is entries; on a chat surface the reply is Markdown — prose, headings, code —
and the entries ride inside it, in a fenced code block whose language token is
`uicast`:

````md
Here's this month's revenue at a glance:

```uicast
{"key":"root","component":"Card","seed":[{"set":"scopes.root.orders","expr":"listOrders()"}],"children":["stat"]}
{"key":"stat","component":"Stat","props":{"expr":"({ label: 'Revenue', value: scopes.root.orders.length })"}}
```

The stat is live — it recomputes from the database on every view.
````

[Streamdown](https://streamdown.ai/) (≥ 2.5) renders Markdown as it streams and
lets a plugin claim a fence language. This package ships that plugin: blocks
tagged `uicast` mount as an [`<EntriesRenderer>`](/react/renderer) under your
chat's `<RendererProvider>`; every other fence stays ordinary highlighted code.
The language token is the entire routing contract — which is why the
[fence prompt partial](/prompt#chat-surfaces) forbids the model from using any
other token for entries.

## `createFenceRenderer`

```ts
import type { CustomRenderer } from "streamdown";

function createFenceRenderer(options?: FenceRendererOptions): CustomRenderer;

type FenceRendererOptions = {
  /** Show a Rendered/Source switcher above each block. Default false. */
  showSourceToggle?: boolean;
};
```

Everything else — implementations, functions, fallback UI — comes from the
[`<RendererProvider>`](/react/renderer) wrapping your conversation, and the
entries come from the fence content: each completed JSONL line is parsed into
an entry and mounts immediately, while the partial last line waits until its
newline arrives. A streaming fence grows into UI line by line, exactly like the
raw-JSONL path.

Call it **once per option set** — at module scope, or inside `useMemo` — and
reuse the returned object:

```tsx
import { Streamdown } from "streamdown";
import { RendererProvider } from "@uicast/react";
import { createFenceRenderer } from "@uicast/streamdown";
import { allImplementations } from "@uicast/shadcn-catalog/impls";
import { tools } from "./tools";

const fenceRenderer = createFenceRenderer();

export function Chat({ replies }: { replies: string[] }) {
  return (
    <RendererProvider implementations={allImplementations} functions={tools}>
      {replies.map((markdown, i) => (
        <Streamdown key={i} plugins={{ renderers: [fenceRenderer] }}>
          {markdown}
        </Streamdown>
      ))}
    </RendererProvider>
  );
}
```

The identity rule is not a style preference. Streamdown re-renders on every
streamed token, and a fresh component type per render would remount the
block each time — re-running [seeds](/entry/state), wiping its state, and
re-firing every host-function call in them. If your options depend on props,
wrap the call in `useMemo`; never call it inline in JSX.

Two behaviors worth knowing:

- **The conversation is one app.** Every block under one `<RendererProvider>`
  renders against the same `root` scope: a write in one block is live in every
  block that reads the path. The prompt partial teaches the model to treat
  `scopes.root` as the app's store — reuse an existing path for the same data,
  introduce new paths for new state — and to seed everything a block reads,
  so a block also works extracted on its own (seeds are first-writer-wins, so
  the repeat costs nothing in the chat). Element keys stay per-fence — only
  state is shared.
- **Blocks mount client-side only.** Seeds call host functions, and host
  functions usually `fetch` browser-relative URLs — running them during SSR
  would fail or double-fire. When a chat page server-renders persisted
  messages, the fence renders nothing until hydration, then mounts.

## `showSourceToggle`

With `showSourceToggle: true`, each block gains a **Rendered / Source**
switcher: Source shows the raw JSONL the model emitted, Rendered shows the
mounted UI. The block stays mounted (hidden) while Source is shown, so
switching back doesn't reset its state. Off by default — it's a
development and demo aid, not end-user chrome.

## Wrappers that forward `plugins`

Chat kits that wrap Streamdown — e.g. AI Elements' response component — usually
apply their own default plugin set and spread your props over it. Passing
`plugins` there **replaces** the defaults, so recompose them alongside the
fence renderer:

```tsx
const plugins = { cjk, code, math, mermaid, renderers: [fenceRenderer] };

<MessageResponse plugins={plugins}>{part.text}</MessageResponse>
```

## `FENCE_LANGUAGE` and `parseFenceCode`

```ts
const FENCE_LANGUAGE = "uicast";

function parseFenceCode(code: string): ComponentEntry[];
```

`FENCE_LANGUAGE` is the token the plugin registers for — import it instead of
retyping the string when you build your own integration. `parseFenceCode` is
the fence-body parser the plugin uses internally: one `JSON.parse` per line,
skipping blank lines, lines that aren't valid JSON, and values that aren't
entries — the same tolerance [`streamJsonLines`](/react/streaming) applies to
raw streams. Exported for hosts that render fences through something other
than Streamdown.

## The prompt side

Rendering is half the contract — the model also has to *know* to emit the
fence. `@uicast/streamdown/prompt` exports `getFencePartialPrompt()`, the
system-prompt section that teaches exactly this syntax and nothing more.
Compose it after the core partials; [Assembling the prompt](/prompt) shows the
full stack.

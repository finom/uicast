# Next.js demo

`packages/nextjs-demo` is a small back office over five Postgres tables (Neon
in production, docker-compose locally): suppliers, products, customers, orders
and a stock ledger. The shell (sidebar, chat panel) is hand-written; every
table, form and detail view is generated. **uicast** calls this the
**front-end-less pattern**.

It is multi-user: everything is world-readable, and only the owner can write.
Log in with OpenRouter (OAuth PKCE; generation bills your own credits) to get a
private copy of the demo data and your own pages and chats under
`/u/<your-slug>`.

## Install and run

```sh
npm install                                   # repo root
docker compose -f packages/nextjs-demo/docker-compose.yml up -d
npm run db:push -w @uicast/nextjs-demo
npm run db:seed -w @uicast/nextjs-demo
npm run dev -w @uicast/nextjs-demo
```

Copy `packages/nextjs-demo/.env.example` to `.env.local`. `DATABASE_URL` works
as is with docker (use a Neon pooled string in production), and `APP_SECRET`
encrypts stored OpenRouter keys (`openssl rand -base64 32{:bash}`). `OPENROUTER_MODEL`
and `AI_MAX_OUTPUT_TOKENS` are optional. There is no site-wide model key.

Then **Create page** for a full generated page, or **New chat** for answers that
render as live UI:

- `Order dashboard with quick status actions`
- `Product catalog with an add-product form`
- `How much did we earn this month?`
- `Help me clear the pending queue`
- `Which products are running low, and who supplies them?`

## What you still write

| You write | The model writes |
|---|---|
| The **data model** — tables, relations, constraints. | Which fields to show, and in what order. |
| The **API** — one endpoint per resource operation. | Which endpoints a screen calls, and when. |
| The **tools** — a typed description of that API. | The calls themselves, inside expressions. |
| The **catalog** — your design system as [def/impl pairs](/def). | The composition: what goes in what, with which props. |

## The tools are your own API

Each tool is a few lines over the REST endpoint a hand-written front end would
call:

```ts filename="src/tools/products.ts"
export const listProducts = standardTool({
  name: "listProducts",
  description: "A page of products, by name by default.",
  inputSchema: productListInput.optional(),
  outputSchema: pageOf(productOutput),
  execute: (input) => apiFetch(`/api/products${query(input ?? {})}`),
});
```

The route validates its query string with the same `productListInput` (from
`src/db/zod.ts`), so the model and the API share one declaration. List tools
take filters, a sort and a window, and return one page of rows with the total.

## The model gets the domain, not the platform

The app's own tables (`users`, `sessions`, `pages`, `component_entries`,
`chats`, `chat_messages`) have endpoints too, but are **left out** of the tool
set:

```ts filename="src/tools/index.ts"
// Page and entry endpoints are excluded: the page system is not the model's to mutate.
export const domainTools: StandardToolV0[] = [
  listCustomers, getCustomer, createCustomer, updateCustomer, deleteCustomer,
  listProducts, getProduct, createProduct, updateProduct, deleteProduct,
  listOrders, getOrder, createOrder, updateOrder, deleteOrder,
  listSuppliers, getSupplier, createSupplier, updateSupplier, deleteSupplier,
  listStockMovements, createStockMovement,
  getSalesSummary, getStockSummary,
];
```

A generated page can create an order. It cannot create a page, edit another
page's entries or read the chat history: it was never given those functions.
Ownership is a second boundary: on someone else's page, the same tools read
that owner's data and the server refuses writes.

## A saved page is rows, not code

Generation streams [entries](/entry) into `component_entries`, one row per line,
keyed by page. Serving the page later is a query and a mount, with no build or
deploy. An edit is another generation on the same page that re-emits only the
changed keys ([partial replacement](/entry#key)).

## Layout

```
packages/nextjs-demo
├── src/db/schema.ts     suppliers · products · customers  (the domain, per user)
│                        orders · stock_movements
│                        users · sessions                  (OpenRouter login)
│                        pages · component_entries         (generated UI, persisted)
│                        chats · chat_messages             (the chat surface)
├── src/db/zod.ts        schemas shared by the tools and the routes
├── src/tools/           24 standard-tools over the REST API
├── src/app/api/         the REST API itself, /api/generate, /api/chat, /api/auth/*
└── src/app/u/[slug]     a user's public index, pages and chats
```

Every domain row carries a `userId`: reads take the owner from the URL
(`?u=<slug>`), writes from the session, and that difference is the whole
read-only mechanism.

Generation streams as described in [Streaming](/streaming), with the prompt
assembled from `defs` and `domainTools` (see [Assembling the prompt](/prompt)).

## Where the pattern stops

A screen with a strict visual contract, such as a marketing page, a print-exact
invoice or a chart with hand-tuned axes, is faster to write than to describe,
and nothing here prevents writing it. A generated screen is only as good as the
components it composes, so once the API exists, the effort goes into
[component definitions](/def).

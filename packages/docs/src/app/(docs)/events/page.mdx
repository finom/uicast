# Event handling

An event is where all three parts of a component meet. The [definition](/def)
names what it carries, the [implementation](/react/impl) fires it, and the
[entry](/entry/fields#callbacks) decides what happens. One object, `evt`, runs
through all three. This page follows a single event across them.

## The same event in three places

`onChange` on a search box: declared once, fired once, handled once.

```ts filename="def.ts"
createComponentDefinition({
  // …
  // the payload schema: what `evt` will carry
  callbacks: {
    onChange: z.object({
      value: z.string().meta({ description: "The current search value" }),
    }),
    onKeyDown: keyboardEventSchema,
  },
});
```

```tsx filename="impl.tsx"
createComponentImplementation({
  // …
  // fire it with a payload that matches the schema
  render: ({ onChange }) => (
    <Input onChange={(e) => onChange({ value: e.target.value })} />
  ),
});
```

```jsonc filename="the entry"
// react to it; `evt` is the payload the impl passed
{ "callbacks": {
  "onChange": [{ "set": "scopes.root.q", "expr": "evt.value" }]
} }
```

The model never sees the def, only what `getComponentsPartialPrompt` prints:

```
  Event handlers:
    - onChange(evt)
      - value: string — The current search value
    - onKeyDown(evt: KeyboardEvent)
```

`onKeyDown` costs one line because `keyboardEventSchema` is a **common event**: a
payload printed once for the whole catalog instead of re-inlined on every
component that fires it. That takes two things, and neither alone is enough:

1. the payload schema carries a JSON Schema **`$id`** — `.meta({ $id: "KeyboardEvent" })`;
2. that same schema is passed to `getComponentsPartialPrompt` as **`commonEvents`**.

Matching is on `$id` alone, and an unregistered payload just inlines as usual.
One with no `$id`, or two sharing one, throws at assembly. The shadcn catalog
ships `allCommonEventSchemas` ready to pass. See [Shared events](/def).

## Following one keystroke

The same search box, with a two-step reaction:

```jsonc
{ "callbacks": { "onChange": [
  { "set": "scopes.root.q",       "expr": "evt.value" },
  { "set": "scopes.root.results", "expr": "searchTasks({ q: scopes.root.q })" }
] } }
```

A user types `abc`:

1. The input's React `onChange` fires; the impl calls `onChange({ value: "abc" })`.
2. The engine binds `evt = { value: "abc" }` and plans the `onChange` steps into
   [dependency waves](/entry/reactivity).
3. Step one writes `scopes.root.q = "abc"`.
4. Step two **reads** `q`, so it waits for that write, then calls the host search
   function and writes its result to `scopes.root.results`.
5. Every `props` / `each` expression that reads `q` or `results` re-evaluates and
   re-renders — the results list updates itself.

The component knew none of this. It emitted a payload; the entry described the
consequence.

## What the engine does with a callback

When the impl calls a callback, the **engine** runs the entry's steps, not the
component. It:

1. binds the impl's payload as `evt`;
2. runs the steps in **[dependency waves](/entry/reactivity)** — a step reading a
   path an earlier step wrote waits for that write, and so does any host-function
   step, so mutations never race. Independent steps run together;
3. evaluates each `expr` against `evt`, `scopes`, the host functions, and
   `currentValue`, then writes the result to the step's `set` path;
4. asks first if a step carries a `confirm`; on cancel, that step **and every one
   after it** are skipped;
5. yields for a tick between waves, so a write lands before a dependent
   expression reads it.

Every callback the def declares is callable, whether or not the entry wired it.
An unwired one is a no-op, so [implementations](/react/impl) never guard.

## Why it's split this way

The split is what makes model-authored behaviour safe.

- **The schema is the shared vocabulary.** It goes into the model's prompt and
  type-checks against the impl, so the `evt` the model reads and the payload the
  impl sends come from one declaration. The engine parses the payload through it
  before the steps run, so a payload missing a field fails loudly instead of
  reaching the model's expression as `undefined`.
- **The impl only sends the payload.** It turns a React event into a payload and knows
  nothing about the reaction. The reaction lives in the entry, as data, which is
  what lets a model express behaviour without touching React.
- **One mechanism covers every interaction.** A DOM-ish payload (`evt.value`), a
  record (`{ hex, h, s, l }`), a range (`{ from, to }`) all travel the same
  def → impl → entry path. There is no separate custom-event API.
- **Effects are explicit and reactive.** Steps are
  [pure expressions](/entry/expressions), and the only way to change document
  state is `set`. So the evaluator that computes `props` also runs events, and
  [reactivity](/entry/reactivity) comes free: a `set` writes a path, and every
  expression reading it re-renders. No event bus, no manual subscriptions.


## Common patterns

**Side-effect step** — no `set`, so the result is evaluated and discarded:

```jsonc
{ "expr": "track({ event: 'search' })" }
```

**Read-modify-write** — `currentValue` is what the `set` path holds before this
write, so the path is named once:

```jsonc
{ "set": "scopes.root.tags", "expr": "[...currentValue, evt.value]" }
```

`scopes.root.tags` was seeded to `[]`, so each event appends to what is already
there.

**Confirm before damage** — [`confirm`](/entry/value-sources#confirmablevaluesourceassignment)
is a sibling key on the step:

```jsonc
{ "callbacks": { "onClick": [
  { "confirm": "Delete every completed task?", "expr": "deleteCompleted()" },
  { "set": "scopes.root.tasks", "expr": "listTasks()" }
] } }
```

Gating the first step is enough — decline, and the refetch never runs either.

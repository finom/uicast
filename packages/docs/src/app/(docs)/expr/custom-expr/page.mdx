# Custom evaluator

## What an evaluator does

Every expression in a document runs on the evaluator you pass to the renderer:

```tsx
import { Evaluator } from "@uicast/expr";

const evaluator = new Evaluator({ functions });

<RendererProvider implementations={impls} evaluator={evaluator}>
  <EntriesRenderer entries={entries} />
</RendererProvider>;
```

For each expression it:

1. **checks** the source against [the language](/expr#the-language), once per
   source;
2. **reports** the `scopes` paths it reads and the host functions it calls, so
   **uicast** knows when to re-evaluate it and what to await;
3. **runs** it with `scopes`, `evt`, `currentValue`, the host functions and the
   language's globals;
4. **checks the result**: only plain data leaves.

`Evaluator` runs step 3 in an interpreter that checks every read and call
under a [budget](/expr#budgets), so the page needs no `unsafe-eval`. A
subclass can hand step 3 to the JavaScript engine instead.

## A faster evaluator

```ts
import { Evaluator } from "@uicast/expr";

export class FunctionEvaluator extends Evaluator {
  protected override toFunction(names: readonly string[], body: string) {
    return new Function(...names, body);
  }
}

const evaluator = new FunctionEvaluator({ functions });
```

**uicast** does not ship this class: copy it. `toFunction` runs once per
expression and gets the arguments `new Function` takes. Steps 1, 2 and 4 stay;
the engine runs step 3.

Same expressions, measured with `npx vitest bench --run --root packages/expr{:bash}`:

| expression | in a document | `Evaluator` | `FunctionEvaluator` |
| --- | --- | --- | --- |
| `scopes.root.count > 0{:ts}` | a `hidden` condition | ~80 ns | ~29 ns |
| `scopes.root.user.name` | any scope read | ~115 ns | ~38 ns |
| template, two interpolations | a text prop | ~255 ns | ~56 ns |
| object literal from scope | every `props.expr` | ~260 ns | ~93 ns |
| `filter`, `map`, `reduce` over 1000 rows | a derived list | 28–63 µs | 0.7–1.9 µs |
| a whole 1000-row table, 5 expressions per row | the realistic worst case | ~0.79 ms | ~0.26 ms |

What it costs:

- **No budget.** Nothing meters the engine; the `budget` option does nothing.
  `"x".repeat(1e9){:ts}` runs.
- **No check at run time.** A name built at run time reaches whatever it names.
  `"abc"["sub" + "str"](1){:ts}` returns `"bc"{:ts}`, and
  `[({}).constructor.constructor][0]("…")(){:ts}` reaches `Function`, which runs
  any code.
- **`unsafe-eval`.** The page's Content-Security-Policy must allow it.

### The model is the first line of defence

Step 1 still refuses what it can see: statements, assignment, regular
expressions, unknown names, methods outside the allow-list. Through a name
built at run time, an expression can do anything the page can: call `fetch`,
read cookies, change the DOM.

So you bet on the author. A production model that follows
[the prompt contract](/prompt) in your own pipeline is a fair bet. A
stranger's prompt is not, and neither is text the model reads on the way: a
user's message, a fetched page, a tool result someone else can write. Any of
them can carry instructions.

The prompt tells the model that text inside data is data, not instructions.
That makes bad output rare. Under `Evaluator`, the interpreter stops it
whether the model meant it or not.

Use `FunctionEvaluator` only when nothing untrusted reaches the prompt: your
own pipeline, an admin tool, your tests.

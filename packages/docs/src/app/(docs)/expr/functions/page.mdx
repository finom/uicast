# Host functions

A document is just data — on its own it reaches no API. **Host functions** are
the bridge: functions you supply, called by name from
[expressions](/expr) (alongside `scopes` and `evt`), sync or async.

Each is a [`standard-tool`](https://standard-tool.js.org/) (`StandardToolV0`): a
`name`, a `description` the model reads to call it, and optional
`StandardSchemaV1 & StandardJSONSchemaV1` input/output schemas. `execute` runs
where the renderer runs — the browser, with the React binding — so reach your
data over HTTP; a database client would ship its credentials to the client.

## Anatomy of a host function

Build one with `standardTool({...})`:

```tsx
import { standardTool } from "standard-tool";
import { z } from "zod";

const suggestPalette = standardTool({
  name: "suggestPalette",
  description: "Given a base hex color, return a small harmonious palette of hex strings.",
  inputSchema: z.object({ hex: z.string() }),
  outputSchema: z.array(z.string()),
  async execute({ hex }) {
    return harmonize(hex);
  },
});
```

The fields:

- **`name`** — what the model writes in an expression (`suggestPalette(...)`).
  Must be a valid JS identifier.
- **`description`** — what it does; the model reads it to decide when to call.
- **`title`** *(optional)* — a human label (`"Suggest palette"`), printed just
  before the description. The model can reuse it for a button or heading.
- **`inputSchema`** *(optional)* — describes the single input argument. It
  validates at call time and becomes the signature in the prompt. Omit it for a
  zero-argument function.
- **`outputSchema`** *(optional)* — the same for the return value. Omitting it
  means *undeclared*, not *returns nothing*. See
  [Undeclared returns](#undeclared-returns).
- **`execute(input)`** — your logic, async or not. `standardTool` wraps it in an
  `async` function either way, and the engine awaits the result before writing
  it. See [Errors](#errors).

Zod 4.2+, Valibot, and ArkType all qualify.

### Errors

An error thrown from `execute` is caught by the engine and classified. Your
input schema rejecting the arguments is the document's fault —
`invalid-arguments`, which the [recovery loop](/error-recovery) can feed back
to the model. Anything else is a `host-function` failure: the host's problem,
not the document's. Both reach [`onError`](/react/renderer). A failed
[`seed`](/entry/fields#seed) also shows the [`error` slot](/react/renderer). In
a [`callback`](/entry/fields#callbacks), the steps after the failed one do not
run, and writes that already happened stay.

## Wiring into the renderer

Collect your tools into an array, bind them on the evaluator, and pass it to
[`<RendererProvider evaluator={...}>`](/react/renderer#evaluator--the-expression-evaluator):

```tsx
import { Evaluator } from "@uicast/expr";
import { EntriesRenderer, RendererProvider } from "@uicast/react";
import * as catalogImpls from "@uicast/shadcn-catalog/all/impls";
import type { StandardToolV0 } from "standard-tool";

const inventoryFunctions: StandardToolV0[] = [
  listProducts,
  createProduct,
  deleteProduct,
];
const evaluator = new Evaluator({ functions: inventoryFunctions });
const impls = Object.values(catalogImpls);

<RendererProvider
  implementations={impls}
  evaluator={evaluator}
>
  <EntriesRenderer entries={entries} />
</RendererProvider>;
```

Create the evaluator **once** (a module constant). It holds the parse cache,
and a new instance per render re-renders the whole tree.

## How the model calls them

Each tool is in scope under its `name` and takes **one argument**, whatever
`inputSchema` declares — or none, when there is no schema. An object schema
means an object:

```js
deleteProduct({ id: scopes.row.id })   // ✅ inputSchema: z.object({ id: … })
deleteProduct(scopes.row.id)           // ❌ same tool, wrong shape
```

A scalar schema is fine too: with `inputSchema: z.string()` the call is
`deleteProduct(scopes.row.id)`, and the prompt prints
`deleteProduct(string)`. An object gives each field a name and a description the
model can read, which is why the catalog's tools use one.

A function whose fields are all optional is still called with an object, or
with nothing: `listProducts()` passes `undefined`, which a bare `z.object`
rejects. Declare the input as `schema.optional()` when the zero-argument form
should be valid; the prompt prints it the same way.

Functions are merged into the expression context **last**, so a tool named
`scopes`, `evt`, or `currentValue` would shadow the engine's own bindings. Those
three are refused at prompt assembly, as are duplicate names:

```ts
standardTool({ name: "scopes", /* … */ });        // ❌ Host function name "scopes" is reserved
standardTool({ name: "evt", /* … */ });           // ❌ reserved
standardTool({ name: "currentValue", /* … */ });  // ❌ reserved
standardTool({ name: "listOrders", /* … */ });     // ✅ anything else is fine
```

## Where they run: `seed` and `callbacks`

Your `execute` can be sync or async, but a call always returns a Promise —
`standardTool` wraps it in an `async` function either way. So a function can
only be called where the engine awaits the result, which is the two effectful
sites:

- **[`seed`](/entry/fields#seed)** — load data on mount. The element shows its
  [placeholder](/react/renderer) until every async seed resolves:

  ```jsonl
  { "key": "table", "component": "Table",
    "seed": [{ "set": "scopes.root.rows", "expr": "listProducts()" }] }
  ```

- **[`callbacks`](/entry/fields#callbacks)** — change something on an event. The
  result is written to the step's `set` path:

  ```jsonl
  { "key": "suggest", "component": "Button",
    "callbacks": { "onClick": [
      { "set": "scopes.root.swatches", "expr": "suggestPalette({ hex: scopes.root.base })" }
    ] } }
  ```

Not in `props`, `hidden`, or `each`. Those run synchronously on every render,
so the engine rejects a host call there as a classified error in the element's
error slot. The rule: **derived values in `props`, effects in `seed` and
`callbacks`.**

### Mutate, then re-fetch

A mutation returns only what it changed, so the usual shape is to call it, then
re-read in the next step:

```jsonl
{ "key": "del", "component": "Button",
  "callbacks": { "onClick": [
    { "confirm": "Delete this product?", "expr": "deleteProduct({ id: scopes.row.id })" },
    { "set": "scopes.root.rows", "expr": "listProducts()" }
  ] } }
```

Step one has no `set` — it runs for its effect alone. A host-function step is a
barrier, so the re-fetch waits for the delete, and `confirm` gates both. Step
ordering in full: [Reactivity](/entry/reactivity#effectful-sites-ordering).

### Windows and aggregates

A function that can return a lot should take a window, and the schema is where
the model learns it:

```ts
standardTool({
  name: "listProducts",
  description: "A page of products, by name by default.",
  inputSchema: z.object({
    limit: z.number().int().min(1).max(200).default(50).meta({ description: "Rows to return." }),
    offset: z.number().int().min(0).default(0).meta({ description: "Rows to skip." }),
    q: z.string().optional().meta({ description: "Matches the name, case-insensitive." }),
  }).optional(),
  outputSchema: z.object({
    items: z.array(product),
    total: z.number().int().meta({ description: "Rows matching the filters, all pages." }),
  }),
  execute: (input) => fetchProducts(input ?? {}),
});
```

The prompt renders the bounds and defaults next to each field, and its rules
tell the model to ask for the slice it renders, to refetch from the callback
that changes the page or a filter, and never to filter or sort a fetched slice
in an expression. Return the count with the rows: a pager needs
`Math.ceil(total / limit)`, and a reduce over one page cannot produce it. A
function that returns rows alone still pages, with `Pagination`'s `hasNext`
(`rows.length === limit`) in place of `totalPages`. Other totals belong in a
function of their own: `getSalesSummary({ days })` returning a count and a sum
is read as data.

## Advertising to the model

The model can only call a function it was told about.
`@uicast/core/prompt` exports `getFunctionsPartialPrompt`:

```ts
import { getFunctionsPartialPrompt } from "@uicast/core/prompt";

getFunctionsPartialPrompt({
  functions: [
    standardTool({
      name: "listProducts",
      description: "Return every product, newest first.",
      outputSchema: z.array(z.object({ id: z.number().int(), name: z.string() })),
      execute: async () => (await fetch("/api/products")).json(),
    }),
    standardTool({
      name: "deleteProduct",
      description: "Delete a product by id.",
      inputSchema: z.object({ id: z.number().int().meta({ description: "Product id." }) }),
      execute: ({ id }) => fetch(`/api/products/${id}`, { method: "DELETE" }),
    }),
  ],
});
```

renders exactly:

```
# Available Functions

listProducts, deleteProduct

# Function Details

- listProducts() => {
    id: number /* integer */;
    name: string;
  }[]: Return every product, newest first.
- deleteProduct({
    id: number /* Product id. integer */;
  }) => unknown: Delete a product by id.
```

One bullet per tool: `name(params) => output: title — description`. A tool
without a `title` prints `name(params) => output: description`. An object type
is printed over several lines, one field per line, and a field's
`.meta({ description })` becomes a comment next to it, followed by what the
type alone does not say: `integer`, bounds (`≥ 1, ≤ 200`), lengths, a
`format`, a `default`. The model sees `limit?: number /* integer, ≥ 1, ≤ 200,
default 50 */` and calls within it. A tool with no `inputSchema` prints empty
parens; one with no `outputSchema` prints `=> unknown`.

Never declare a schema for "nothing" — `z.void()` has no JSON Schema form and
throws.

A type shared by two functions prints once under `# Shared Types` — see
[Shared types](#shared-types).

## Undeclared returns

`=> unknown` means **nobody published this shape**. The prompt tells the model
it may call the function for its effect, but must not read fields off the
result:

```jsonc
// what the prompt printed for the two:
//   deleteProduct({ id: number }) => unknown
//   listProducts() => { id: number; name: string }[]

// ✅ delete for the effect, then refetch through the declared one
[ { "expr": "deleteProduct({ id: scopes.row.id })" },
  { "set": "scopes.root.products", "expr": "listProducts()" } ]

// ❌ store the `unknown` result and read fields off it
{ "set": "scopes.root.result", "expr": "deleteProduct({ id: scopes.row.id })" }
// … later: scopes.root.result.remaining — nothing ever said `remaining` exists
```

A step with **no `set`** is legal only in `callbacks`, so a function returning
`unknown` has no place in a `seed`.

`outputSchema` matters more here than in ordinary tool calling. A chat model
sees the response before reasoning about it. Here the model writes
`scopes.root.products[0].name` into an expression that runs later, against data
it never sees.

## Shared types

A named schema is printed once as a type and referenced by name everywhere it is
used. In Zod that is `.meta({ id })`:

```ts
const Person = z
  .object({ id: z.string(), name: z.string().optional() })
  .meta({ id: "Person" });
```

```
# Function Details

- getOwners() => {
    owner?: Person;
    reviewer?: Person;
  }: Owners.
- listTree() => {
    root?: Node;
  }: Whole tree.

# Shared Types

- Person: { id: string; name?: string }
- Node: { name?: string; children?: Node[] } — A folder or file.
```

Without the `.meta({ id })`, `Person` is inlined at both sites instead.

[Components](/def) hoist their own types into a separate `# Shared Types` block;
nothing crosses between the two.

This does two things. A type used by ten functions is printed once instead of
ten times. And a **recursive** type becomes possible to express at all: inlined,
its self-reference stops at the cycle guard and prints `unknown[]`, which says
the tree is one level deep.

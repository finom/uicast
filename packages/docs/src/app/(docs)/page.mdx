**uicast is a UI framework whose language is written by models, not people.**
It gives a language model what JSX gives a developer — components, state,
events. The difference: JSX is designed to be easy for a person to maintain,
**uicast** to be reliable for a model to generate.

The model writes one JSON object per line. The engine places each line in the
tree and wires it to a reactive state store, and the result is a working
front-end app. The lines are just data, so there is no build or deploy step per
page.

What makes **uicast** different is **expressions**.

Structured generation renders safely as it streams, but the logic wiring its
components is a closed vocabulary — a fixed set of bindings, conditions, and
format operators, so a genuinely new computation means new host code. **uicast**
makes that logic open-ended JavaScript instead: computed values, visibility, and
event handling are expressions, run by a
[closed-grammar interpreter](/expr) — JavaScript's shape, without the
JavaScript engine.

```js
// scopes.root.orders === [{ total: 2 }, { total: 3 }]
scopes.root.orders.reduce((a, o) => a + o.total, 0)  // ✅ → 5
listOrders()                                         // ✅ a host function you registered,
                                                     //    callable in seed and callbacks
fetch("/api/orders")                                 // ❌ throws — "fetch" is not
                                                     //    available in expressions
document.cookie                                      // ❌ throws — so do "window",
                                                     //    "localStorage", "eval", …
```

| Approach | Predictability | Expressiveness | Safety |
| --- | --- | --- | --- |
| Raw code generation | low | unlimited | low |
| **uicast** | high | high | high |
| Structured generation ([json-render](https://github.com/vercel-labs/json-render), [A2UI](https://a2ui.org)) | deterministic | limited | guaranteed |

## Is it safe?

By default, expressions never reach `eval` or `new Function`. They run on an
[interpreter](/expr) built for a **fraction of JavaScript**: a closed
grammar, an allow-list of methods and globals, a check on every property read,
and a CPU and allocation budget. The JavaScript engine never executes generated
text, so a uicast app runs under a strict Content-Security-Policy — no
`unsafe-eval`.

Need more speed? The evaluator has two modes. `interpret` (the default) is the
interpreter above; it trusts nothing. `native` validates against the same
grammar, then runs the expression with `new Function` — near-native speed, for
documents from a trusted author: your own pipeline, an admin, never a stranger.
There [the model is your first line of defence](/expr#the-model-is-your-first-line-of-defence).

The interpreter secures the language, not what you plug into it — host functions
are capabilities you grant, and scope data is only as safe as what you put
there. [The expression evaluator](/expr) covers the full threat model.

## The model works from a developer's brief

The model never starts from a blank page. It gets the brief you would give a new
front-end developer — the components and the endpoints, generated from your code:

```md
# Available Components

Card, Heading, Text, Badge, Button, Table, TableRow, TableCell

# Component Details

- Button — A clickable button.
  Props:
    - text?: string — The button label
    - variant?: "default" | "destructive" | "outline" | …
  Event handlers:
    - onClick(evt: MouseEvent)

… one entry per component …

# Available Functions

listOrders, refundOrder

# Function Details

- listOrders() => { id: number; customer: string; total: number }[]: Every order, newest first.
- refundOrder({ id: number }) => unknown: Refund one order.
```

> Show this week's orders, with refund buttons.

Both lists are fixed: the **catalog** is your design system, so the model picks
a component and never invents one; the **functions** are your endpoints, each a
[`standard-tool`](https://standard-tool.js.org/), and it can call nothing else.
Every description is one you already wrote on a prop or schema field, passed
through word for word. A developer with this brief writes JSX; the model writes
**uicast** entries — see [Assembling the prompt](/prompt).

## Events carry declared payloads

An event can carry data. The square below sends the pointer position as an
`onMove` payload; the entry writes it to state, and the props read it back. No
host function is involved.

Inside a callback, **`evt` is that payload** — the only way to read what the
user just did. It is not React's `SyntheticEvent`; its shape is whatever the
[definition](/def) declares, so `onMove` here means `evt.x` and `evt.y` are
numbers.

## Expressions call host functions

Expressions can call **host functions** — the functions you register with the
renderer, and how a document reaches a backend. Each is a
[`standard-tool`](https://standard-tool.js.org/): a name, a description,
schemas, and `execute`.

`getWeather` below is **async**, about 500 ms. Picking a city runs a two-step
callback: the first stores the city, the second calls
`getWeather({ city: scopes.root.city })` and reads the path the first just
wrote, so the runtime orders them. The engine waits for the async result before
writing it to state.

## Chat replies carry live UI

A model's Markdown reply can stream a working app inline, not just static text.
The [Streamdown](/streamdown) plugin renders any `uicast` fenced block as a live
[`<EntriesRenderer>`](/react/renderer) inside the streamed Markdown, leaving
every other fence as highlighted code:

````md
Here are this week's orders:

```uicast
{"key":"orders","component":"Table", … }
```

Want me to refund any of them?
````

The whole chat runs under one [`<RendererProvider>`](/react/renderer), so every
widget streamed into it shares the same `root` scope and can share state. Yet
each fenced block is a complete document on its own — lift one out and it renders
standalone, so a widget the user likes can be saved as its own view. See the
[Streamdown plugin](/streamdown).

# Host functions

A generated document is just data — on its own it can't reach a database, call
an API, or change anything. **Host functions** are the bridge: real async
functions *you* supply, which the model's [expressions](/entry/expressions) call
by name to load data and commit changes. They're the third kind of callable an
expression sees, alongside `scopes` (state) and `evt` (the event payload).

Each one is a [`standard-tool`](https://standard-tool.js.org/) — a
self-describing function with a `name`, a `description`, and optional input /
output schemas built on [Standard Schema](https://standardschema.dev). That
self-description is exactly what lets the **model** know a function exists and
how to call it (see [Advertising to the model](#advertising-to-the-model)).

**`StandardToolV0`** is the interface uicast builds on — the v0 surface of
`standard-tool`, and the type every seam that takes host functions is written
against: [`<RendererProvider functions>`](/react/renderer),
[`evaluate`](/core#expressions)'s `options.functions`, and
[`getFunctionsPartialPrompt`](/core#prompt--uicastcoreprompt). uicast never
defines its own tool type: anything satisfying `StandardToolV0` works, whoever
produced it.

## Anatomy of a host function

Build one with `standardTool({...})`:

```tsx
import { standardTool } from "standard-tool";
import { z } from "zod";

const suggestPalette = standardTool({
  name: "suggestPalette",
  description: "Given a base hex color, return a small harmonious palette of hex strings.",
  inputSchema: z.object({ hex: z.string() }),
  async execute({ hex }): Promise<string[]> {
    // …derive and return the palette
  },
});
```

The fields:

- **`name`** — the identifier the model emits in an expression
  (`suggestPalette(...)`). Must be a valid JS identifier.
- **`description`** — one line of what the function does; the model reads it to
  decide when to call it.
- **`inputSchema`** *(optional)* — a schema that is both a runtime validator and
  serializable to JSON Schema (`StandardSchemaV1 & StandardJSONSchemaV1` — the
  pair core aliases as `CombinedSpec`; Zod 4.2+ qualifies, as does any library
  exposing `~standard.jsonSchema`), describing the single input argument. It both **validates** the input at call
  time and **emits JSON Schema** that the prompt turns into a signature. Omit it
  for a zero-argument function.
- **`outputSchema`** *(optional)* — the same, for the return value.
- **`execute(input)`** — your logic. Receives the validated input and returns
  the output, normally as a `Promise` (host functions are async by nature). It
  **throws** on failure — see [Errors](#errors).

### Errors

`execute` **throws on failure** by default — a thrown error from your logic, or a
`StandardToolValidationError` on a schema mismatch. That's exactly what a live
rendered UI wants: a failed [`seed`](/entry/fields#seed) surfaces through the
renderer's [`error` slot](/react/renderer) (the same path a render throw takes), and a
failed [`callback`](/entry/fields#callbacks) step aborts the whole callback —
every later step is skipped, dependent or not, while writes already applied
(including the failing step's parallel peers in its own wave) stay — instead of
silently resolving to a value the expression then treats as data. The engine
catches it rather than letting it reject: it classifies the error and reports it
through [`onError`](/react/renderer), the only channel a callback has. No error wrapping to wire up on your side.

Whatever escapes `execute` is classified as an
[`EntryError`](/error-recovery#classification-entryerror-and-onerror) with
reason `host-function` — an **environment** fault, since asking the model to
re-emit the element won't fix your API being down. When the failure is really
the *document's* fault — the arguments validate but make no sense, like an `id`
for a row that doesn't exist — throw an `EntryError` yourself to say so:

```ts
import { EntryError } from "@uicast/core";

async execute({ id }) {
  const order = await db.orders.find(id);
  if (!order)
    throw new EntryError(`No order with id ${id}`, { reason: "invalid-arguments" });
  return order;
}
```

`invalid-arguments` classifies as a **document** fault, so
[recovery](/error-recovery) knows this one *is* worth feeding back to the model.

One asymmetry worth knowing: `inputSchema` validation runs **inside** the
wrapped `execute`, so a malformed argument object throws a
`StandardToolValidationError` that files as `host-function` /
**environment** — even though the document caused it, which means self-healing
skips it. To have the model fix its own argument shapes, re-tag it outside the
tool: wrap the `standardTool()` result and, in the `catch`, re-throw an
input-target validation error as
`new EntryError(err.message, { reason: "invalid-arguments" })`. Output-schema
mismatches are genuinely yours — leave those as `host-function`.

> **Request context** (an auth token, a DB handle, the current user) — **close
> over it** when you define the function. The engine calls `execute(input)` with
> just that one argument, and the functions array is host-built, so each function
> can capture whatever the host has.

## Wiring into the renderer

Collect your tools into an array and pass it to
[`<RendererProvider functions={...}>`](/react/renderer):

```tsx
import { EntriesRenderer, RendererProvider } from "@uicast/react";
import { allImplementations } from "@uicast/shadcn-catalog/impls";
import type { StandardToolV0 } from "standard-tool";

const inventoryFunctions: StandardToolV0[] = [
  listProducts,
  getCategoryBreakdown,
  createProduct,
  updateProduct,
  deleteProduct,
];

<RendererProvider
  implementations={allImplementations}
  functions={inventoryFunctions}
>
  <EntriesRenderer entries={entries} />
</RendererProvider>;
```

Like `implementations`, pass a **stable reference** (a module constant) — it folds
into the provider's context, so rebuilding the array each render would re-render
the whole tree.

## How the model calls them

The engine exposes each tool inside expressions as a function keyed by its
`name`, so the model writes a normal call with **a single object argument**
matching `inputSchema` (or no argument for a schema-less tool):

```js
deleteProduct({ id: scopes.row.item.id })   // ✓ one object matching inputSchema
deleteProduct(scopes.row.item.id)            // ✗ positional scalar — wrong shape
```

A host-function name **shadows** a same-named scope variable (functions are
merged into scope last), so keep tool names distinct from your scope keys.

**No `await`.** Host functions are async, but the engine awaits a step's result
before writing it to the `set` path, so the bare call is enough — and the prompt
tells the model to write exactly that (`listProducts()`, never
`await listProducts()`), so that is what generated documents contain.

## Where they run: `seed` and `callbacks`

Host functions are **async**, so they may only be called where the engine can
`await` them — the two *effectful* expression sites:

- **[`seed`](/entry/fields#seed)** — load initial data on mount. The element
  **suspends** (showing its [placeholder](/react/renderer)) until every async seed
  resolves:

  ```jsonl
  { "key": "table", "component": "Table",
    "seed": [{ "set": "scopes.root.rows", "expr": "listProducts()" }] }
  ```

- **[`callbacks`](/entry/fields#callbacks)** — commit a change in response to an
  event. The step's result is written to its `set` path:

  ```jsonl
  { "key": "suggest", "component": "Button",
    "callbacks": { "onClick": [
      { "set": "scopes.root.swatches", "expr": "suggestPalette({ hex: scopes.root.base })" }
    ] } }
  ```

They are **not** for the reactive sites — `props`, `hidden`, `each`. Those
evaluate synchronously on every render: they can't `await` a Promise (a host
call there would hand the expression a pending Promise, not data), and a render
must stay [pure](/entry/expressions#pure-and-stateless) — no side effects. The
engine technically puts the call wrappers in scope everywhere, but the rule is
simple: **derived values go in reactive `props`; effects go in `callbacks` and
`seed`.**

### Callback step mechanics

A callback runs its steps in **dependency order**: a step that calls a host
function always waits for the steps before it — a mutation's effect is
invisible to path analysis, so effectful steps never race — and a step that
reads a path an earlier step `set` (including via `currentValue`) waits for
that write. Pure assignment steps with no dependency on each other may run
together. When a step has a `set`, the resolved value is written through the
reactive store (waking every subscriber of that path and of any path beneath
it); between waves
the engine yields to the event loop, so a write's reactive update flushes
before a dependent step reads scope. A step with no `set` runs purely for its
side effect. Because a mutation returns only the row it changed, the usual
shape is to **chain a re-read** after a write:

```jsonl
{ "key": "del", "component": "Button",
  "callbacks": { "onClick": [
    { "expr": "deleteProduct({ id: scopes.row.item.id })" },
    { "set": "scopes.root.rows", "expr": "listProducts()" }
  ] } }
```

A step may also carry a [`confirm`](/entry/fields#callbacks) prompt; if the user
cancels, that step **and all later steps** are skipped.

## Advertising to the model

For the model to emit a call, it has to know the function exists.
`@uicast/core/prompt` exports `getFunctionsPartialPrompt`, which renders your
tools into a prompt block — a names list plus one TypeScript-style signature per
tool, derived from the schemas. For example:

```
# Available Functions

listProducts, createProduct, deleteProduct

# Function Details

- listProducts() => { id: number; name: string }[]: Return every product, newest first.
- createProduct({
    name: string;
    price: number;
  }) => {
    id: number;
  }: Add a product. Returns it.
- deleteProduct({ id: number }) => void: Delete a product by id.
```

The signature is `name(params) => output: description`. No `inputSchema` renders
empty parens (`listProducts()`); no `outputSchema` renders `=> void`. So express
"**returns nothing**" by **omitting** `outputSchema` — never `z.void()`, which
has no JSON Schema form and throws. The block is catalog-agnostic: you compose
it into your larger system prompt alongside the [component
menu](/def#registration), passing whatever tools you choose to expose.
